# OmniLink Project Skills

This file is the project-local skill constitution for OmniLink. Every development turn must read this file first, match the current task against active project-specific skills, and only then use general skills as the technical base.

## Origin Protocol

Source: 起源版专属 Skill 架构师, V4.2 三相钩子版.

### Dispatch Hook

For each user request:

1. Read `.project-skills.md`.
2. Extract the current intent.
3. Match active `Project-Specific-*` skills.
4. Decide whether an official/general skill is needed as the temporary technical base.
5. Choose the decision mode.
6. Execute the task.
7. End-of-turn audit:
   - Did this turn create project-specific logic?
   - Is it high complexity or likely to be reused at least twice?
   - Should a skill be added, updated, deprecated, degraded, or fused off?

### Decision Modes

- Ascetic Mode: conservative, deterministic, for security, permissions, data migration, high-risk refactors, and core governance.
- Tidewatcher Mode: default mode for daily OmniLink development, docs, scripts, UI, and integration work.
- Ranger Mode: exploratory mode for naming, narrative, concept design, and clearly requested divergent ideas. Ranger output must not overwrite stable project skills unless the human explicitly accepts it.

### Stable Decision Anchors

Use these anchors when deciding whether to add, modify, deprecate, degrade, or fuse off a project skill:

- Project name: OmniLink.
- Current repository structure.
- Current branch and latest commit when available.
- Current `.project-skills.md` summary.
- Current user request summary.
- Existing related decision records.

### Skill Lifecycle

- New skill threshold: existing skills do not cover the need, and the logic is high complexity or likely to be reused at least twice.
- New skill naming: `Project-Specific-[Module]-[Feature]`.
- Project fit outranks cross-project reuse.
- If a skill causes logic errors, immediately degrade it for the current session, mark it `[status: abnormal/pending-fix]`, and fall back to general best practices until the human approves a correction.

## Active Project-Specific Skills

### Project-Specific-Web-MockAdapterBoundary

Status: active.

Scope:

- `packages/web/src/lib/wallet.js`
- `packages/web/src/lib/config.js`
- `packages/web/src/lib/http.js`
- `packages/web/src/lib/registry.js`
- `packages/web/src/lib/peer.js`
- `packages/web/src/lib/aiClient.js`

Purpose:

Keep OmniLink Web development unblocked while contract, P2P device, and AI Agent services are still changing.

Inputs:

- Wallet state from TronLink or mock fallback.
- Device registry records with `id`, `name`, `type`, `owner`, `status`, `access`, `expiresAt`, `connection`, and `lastEvent`.
- Device command payload `{ deviceId, action }`.
- Agent request payload `{ message, devices }`.

Expected outputs:

- Wallet adapter returns `{ address, network, source }`.
- Registry adapter returns devices and access/grant results.
- P2P adapter returns `{ ok, requestId, deviceId, action, transport, receivedAt }`.
- AI adapter returns `{ reply, toolCall }`, where `toolCall.arguments` can be passed to `sendDeviceCommand`.

Implementation rules:

- UI components must not call chain, P2P, or AI service details directly.
- Replace mock behavior by editing adapter files, not by rewriting panels.
- Keep mock fallback working unless the human explicitly asks for production-only behavior.
- Any new integration surface must first define an adapter contract in `packages/web/src/lib`.
- API URLs must be read from Vite environment variables, documented in `packages/web/.env.example`, and paired with `docs/api-contracts.md`.
- API failure must preserve the demo path by falling back to mock behavior unless the human explicitly requests hard failure.

Failure fallback:

- If TronLink is missing, use the mock wallet.
- If a team-owned service is unavailable, preserve local demo behavior and log the integration gap in `docs/status.md`.
- If an API URL is configured but fails, keep UI state alive, return a mock result with `source` and `fallbackReason`, and log the failure to the console.

### Project-Specific-Web-DemoClosedLoop

Status: active.

Scope:

- `packages/web/src/App.jsx`
- `packages/web/src/components/*`
- `packages/web/src/styles.css`

Purpose:

The Web app must always preserve a hackathon-demo closed loop: connect wallet -> inspect device -> check or grant access -> send device command -> ask Agent -> execute suggested tool.

Inputs:

- Current selected device.
- Current wallet.
- Current event log.
- Current Agent message.

Expected outputs:

- User can complete the full demo path even before backend integration.
- Each important action appends a human-readable event to the integration log.
- The UI remains usable on desktop and mobile.

Implementation rules:

- Do not ship inert controls for the core demo path.
- If a real API is not ready, keep the same visible workflow with mock data.
- Keep the event log capped and readable.
- Prefer stable buttons, panels, and explicit states over hidden magic.

Failure fallback:

- If a command cannot be sent, show a clear UI event instead of silently failing.
- If a device is offline, keep unsafe actions disabled and explain through current device state or event log.

### Project-Specific-Web-IntegrationStatus

Status: active.

Scope:

- `docs/status.md`
- `README.md`
- Any future integration docs under `docs/`

Purpose:

Keep team integration facts in repository Markdown so humans and AI can both read the current state.

Inputs:

- Contract ABI/address needs.
- Device/P2P signaling and command schema needs.
- AI Agent chat and function-call response needs.
- Current frontend adapter files.

Expected outputs:

- `docs/status.md` lists today status, integration contracts needed, and Web mock adapter files.
- README exposes the fastest command for running the frontend.

Implementation rules:

- When adding or changing an integration boundary, update `docs/status.md` in the same turn.
- Do not bury integration contracts only in chat history.
- Keep docs concise and execution-oriented for hackathon speed.

Failure fallback:

- If exact upstream API details are unknown, record the unknown as a blocker or needed contract instead of inventing final API facts.

### Project-Specific-Web-DemoOrchestration

Status: active.

Scope:

- `packages/web/src/components/DemoConsole.jsx`
- `packages/web/src/lib/health.js`
- `packages/web/src/App.jsx`
- `docs/api-contracts.md`
- `docs/backend-api-implementation.md`

Purpose:

Give OmniLink a repeatable hackathon control surface for team integration and live demos.

Inputs:

- Current wallet.
- Current selected device.
- Current device list.
- Adapter health derived from Vite API URLs and `GET /health`.
- Adapter functions for wallet, registry, P2P, and AI.

Expected outputs:

- Service statuses display as `mock`, `connected`, or `failed`.
- One-click demo runs: connect wallet -> check access -> grant 24h -> unlock device -> ask Agent -> run Agent tool.
- Each step writes a readable event to the integration log.

Implementation rules:

- Demo orchestration must call existing adapter functions instead of duplicating service logic.
- The console must preserve mock mode and remain useful before backend services exist.
- Backend docs must include `GET /health` whenever the console depends on health checks.
- A failed service must not block mock fallback unless the human explicitly requests strict integration mode.

Failure fallback:

- If no selected device exists, log `Demo flow blocked`.
- If a step throws, log `Demo flow failed` and keep the UI interactive.
- If a health endpoint fails, show `failed` for that service without crashing the app.

### Project-Specific-Web-I18nMode

Status: active.

Scope:

- `packages/web/src/lib/i18n.js`
- `packages/web/src/components/LanguageToggle.jsx`
- `packages/web/src/App.jsx`
- `packages/web/src/components/*`

Purpose:

Keep the OmniLink Web demo bilingual for Chinese-first team development and English hackathon judging.

Inputs:

- Current language code: `zh` or `en`.
- Translation key strings from `packages/web/src/lib/i18n.js`.
- User-selected language stored in `localStorage`.

Expected outputs:

- Default language is Chinese.
- Users can switch to English from the top bar.
- Core demo UI, integration console, controls, and event titles use translation keys.

Implementation rules:

- Do not hardcode new user-facing UI text in components when it belongs in the translation table.
- Keep the language switch local and lightweight; do not add a routing or heavy i18n framework unless the app grows beyond the hackathon surface.
- Dynamic technical values such as API names, device IDs, transaction IDs, and source labels may stay literal.

Failure fallback:

- Missing translation keys must fall back to the key name rather than crashing the UI.
- If `localStorage` has no value, use `zh`.
